# Milestone 6 Plan: Retire Review Items

Status: implementation plan.

This plan covers the milestone-6 migration from persisted `review_items` to
study actions and word-skill scheduler state.

Related documents:

- [`study-action-model.md`](/Users/jw/dev/chinese-study-app/SPECS/study-action-model.md)
- [`learning-review-model.md`](/Users/jw/dev/chinese-study-app/SPECS/learning-review-model.md)
- [`session-covering-criteria.md`](/Users/jw/dev/chinese-study-app/SPECS/session-covering-criteria.md)

## Goal

Exit milestone 6 with `review_items` removed as a durable table.

The replacement architecture should use:

- `words` for word lifecycle state
- `word_skill_state` for recognition/production review scheduling
- `word_study_admission_state` for review-phase word admission
- generated session actions for live session work
- durable attempt events as evidence for review projections

`review_items` should not remain the session composition root, the review
commit target, or the learning/unstudied directional-task source.

## Current Dependency Summary

Review scheduling is already partly migrated. Review session composition admits
review words through `word_skill_state` and `word_study_admission_state`, then
joins `review_items` mostly to manufacture the legacy `SessionItemWithWord`
shape expected by the frontend.

The remaining dependencies are:

- frontend session runtime uses `reviewItem.id` as the session unit key
- frontend session runtime uses `reviewItem.direction` as the direction/skill
  signal for recognition vs production
- learning and unstudied session buckets are generated by joining words to
  persisted `review_items`
- accepted review attempt batches still update `review_items` before projecting
  events into `word_skill_state`
- dashboard and Words page inspection endpoints still expose review-item-shaped
  data
- schema/bootstrap/import scripts still create and seed `review_items`
- tests still set up, mutate, or validate `review_items`

The most important decoupling is therefore not merely swapping SQL tables. It is
introducing a first-class live session unit that is not backed by a persisted
review-item row.

## Target Session Unit

Introduce a new frontend/backend session item type that represents recall or
assessment work served inside a session.

Conceptual shape:

```ts
type SessionStudyItem = {
  sessionActionId: string;
  actionKind: 'recognition' | 'production' | 'contrast_selection';
  targetWordId: string;
  sampledSkillIds: StudySkillId[];
  contentRef: StudyContentRef | null;
  word: Word;
};
```

For milestone 6, only recognition and production need to be generated.

The backend should join the selected action with word table data before sending
the session payload. The frontend needs the full word payload to render prompts,
answers, meanings, pinyin, notes, and examples. This keeps the live session
self-contained after composition, consistent with the existing frontend-owned
in-flight session model.

Session source is carried by the bucket, not duplicated on every item:

```ts
type SessionStudyItemBuckets = {
  review: SessionStudyItem[];
  learning: Word[];
  unstudied: Word[];
};
```

The active frontend unit may be a small union:

```ts
type ActiveSessionUnit =
  | { type: 'study'; bucket: 'review' | 'learning' | 'unstudied'; item: SessionStudyItem }
  | { type: 'unstudied_intro'; word: Word };
```

The intro unit is deliberately not a `SessionStudyItem` because it is not a
recognition or production attempt. It is the first-encounter presentation before
unstudied recall drilling begins.

The bucket is first-class because the session covering rules still depend on the
word's lifecycle role in the session:

- `unstudied`: hard-coded first-encounter covering criteria
- `learning`: hard-coded learning covering criteria
- `review`: backend-selected skill/action assessment

This is distinct from the action kind. For example, both learning and review can
serve a production action, but the covering and commit semantics differ because
the bucket differs.

The `sessionActionId` should be stable within a composed session payload and
safe to use as the frontend progress key. It does not need to be durable across
sessions.

Possible V0 ids:

- review: `review/{wordId}/{skillId}`
- learning: `learning/{wordId}/{skillId}`
- unstudied: `unstudied/{wordId}/{skillId}`

The exact string format is not a product API guarantee. It only needs to be
deterministic for the current session payload and unambiguous in tests.

## Direction And Skill Mapping

Milestone 6 should retire review-item language without losing the simple V0
mapping:

| Legacy direction | Skill | Action kind |
| --- | --- | --- |
| `forward` | `recognition` | `recognition` |
| `reverse` | `production` | `production` |

Frontend prompt/answer logic can continue to branch on action kind or sampled
skill:

- recognition prompt: Hanzi
- recognition answer: meaning plus pinyin
- production prompt: visible production meaning
- production answer: Hanzi plus pinyin

Learning and unstudied coverage rules still need both recognition and
production to be covered, but they should no longer require persisted scheduler
rows.

## Target Scheduler Behavior

The frontend scheduler should choose work in two stages.

First, choose a nonempty bucket by weighted policy:

| Bucket | Weight |
| --- | ---: |
| review | 50 |
| learning | 30 |
| unstudied | 20 |

If the initially sampled bucket is empty, the implementation may either resample
until a nonempty bucket is selected or normalize the weights across currently
nonempty buckets. The observable behavior should be equivalent.

Second, ask the selected bucket for its next served action:

- review bucket: keep the backend-composed order and serve the next
  `SessionStudyItem`
- learning bucket: treat words as an unordered/randomized pool; when a word is
  selected, choose an uncovered recognition or production action based on
  in-session progress
- unstudied bucket: treat words as an unordered/randomized pool; if the word has
  not completed intro, serve an intro unit first; otherwise choose a recognition
  or production action whose 3-Good streak is incomplete

Learning and unstudied selection should happen by word first, then action within
that word. This prevents words with two open skills from being overrepresented
relative to words with one open skill.

The active served recall/assessment exercise can still be represented as a
`SessionStudyItem`. The buckets do not all need to contain pre-expanded
`SessionStudyItem` rows.

## Implementation Phases

### Phase 1: Add SessionStudyItem In Parallel

- Add shared TypeScript types for `SessionStudyItem` and session buckets.
- Keep existing `ReviewItem` types temporarily for compatibility.
- Add mapping helpers from word-skill rows to review-phase session study items.
- Add mapping helpers from words to synthetic learning/unstudied recognition
  and production session study items.
- Update tests for the pure mapping helpers first.

Expected result: the codebase can represent the new live session unit without
changing runtime behavior yet.

### Phase 2: Replace Frontend Scheduler With Bucket Policies

- Replace the current single scheduler of pre-expanded session rows with a
  bucket scheduler.
- Use weighted top-level bucket selection:
  - review: 50
  - learning: 30
  - unstudied: 20
- Preserve the current backend review ordering inside the review bucket.
- Model learning as a randomized pool of words not yet covered today.
- Model unstudied as a randomized pool of selected new words not yet completed.
- Materialize an active `SessionStudyItem` from the selected bucket:
  - review: use the backend-provided review action
  - learning: derive recognition/production from word progress
  - unstudied: derive recognition/production from word progress after intro
- Represent unstudied intro as a distinct active unit rather than an action
  kind.
- Replace `SessionItemWithWord.reviewItem.id` progress keys with
  `sessionActionId` for active served actions where action identity is needed.
- Replace `reviewItem.direction` branching with action kind or skill branching.
- Use the active bucket for covering rules and commit semantics:
  - unstudied bucket commits `completeUnstudiedWordSession`
  - learning bucket commits `completeLearningSession`
  - review bucket commits accepted attempt events and projects word-skill state
- Rename frontend concepts where useful:
  - `ReviewItemProgress` -> `SessionActionProgress` or
    `ReviewActionProgress`
  - `reviewProgress` -> `actionProgress` or `reviewActionProgress`
  - `startedItemIds` -> `startedActionIds`
- Keep learning and unstudied progress keyed by word id.
- Drain mode should keep open work:
  - active item
  - review actions in lapse/reinforcement progress
  - learning words with progress
  - unstudied words with intro or drill progress
- Keep user-visible copy changes modest, but remove "review item" language
  from live-session surfaces where it no longer describes the model.

Expected result: frontend session behavior no longer treats learning and
unstudied work as persisted directional rows, and review action identity is the
only remaining legacy bridge.

### Phase 3: Compose All Session Buckets Without Review Items

- Generate review bucket rows from `word_skill_state`,
  `word_study_admission_state`, and `words`.
- Generate the learning bucket from pending learning words.
- Generate the unstudied bucket from selected unstudied words.
- Preserve existing learning and unstudied covering behavior.
- Preserve the word-level unstudied intake limit.
- Update session composition tests around behavior rather than legacy row ids.

Expected result: `/api/session-payload` does not read `review_items`.

### Phase 4: Project Review Attempts Directly To Word-Skill State

- Change review commit intent from `reviewItemId` to session action identity
  plus target word and skill/action information.
- Validate accepted attempt events against the supplied action identity, target
  word, and sampled skill.
- Remove `updateReviewItemSessionWithoutTransaction` from the accepted attempt
  batch path.
- Keep projection through `projectReviewAttemptEventsWithoutTransaction`.
- Return an empty success response from the endpoint instead of a `ReviewItem`.
- Remove the old `/api/review-items/:id/complete-session` route if no caller
  remains.

Expected result: review completion writes only events, `word_skill_state`, and
`word_study_admission_state`.

### Phase 5: Port Inspection And Overview Reads

- Replace Home overview's due review count with a word-skill/admission query.
- Decide whether the count means due skills or admitted due words. Prefer the
  count that matches session composition.
- Replace the Words page review-item inspector with word-skill state rows.
- Rename API payload fields from review-item language only where the contract is
  already being touched.

Expected result: dashboard and inspection views no longer require
`review_items`.

### Phase 6: Remove Shadow And Backfill Scaffolding

- Remove `validateReviewItemStudySchedulerShadow`.
- Remove the shadow check script or repurpose it to validate scheduler-state
  invariants without `review_items`.
- Remove `backfillStudySchedulerStateFromReviewItems`.
- Remove `mirrorWordReviewItemsToWordSkillState`.
- Replace any bootstrap assumptions that count `review_items`.

Expected result: migration helpers no longer treat `review_items` as the source
of truth.

### Phase 7: Drop Schema And Data Creation

- Remove `CREATE TABLE review_items` from app schema setup.
- Remove `idx_review_items_due`.
- Remove schema assertions for `review_items`.
- Update dev seed creation to create words, meanings, scheduler state, and
  admission state directly.
- Update import scripts to populate `word_skill_state` and
  `word_study_admission_state` directly.
- Decide how to handle existing study databases:
  - either perform a one-way migration that backfills scheduler state from
    existing `review_items` and then drops the table
  - or require a pre-milestone export/import if the active study DB is already
    known to have complete scheduler state

Expected result: new databases are created without `review_items`.

### Phase 8: Delete Legacy Types And Tests

- Remove `ReviewItem` from shared frontend types if no external payload needs
  it.
- Remove `buildLegacyReviewStudyAction` and legacy review-item adapter tests.
- Update tests that manually insert `review_items`.
- Keep focused coverage for:
  - review word admission from word-skill state
  - learning word synthetic recognition/production actions
  - unstudied word synthetic recognition/production actions
  - review attempt event projection
  - Home overview count matching session composition semantics

Expected result: `rg review_items` should find only migration notes or archived
SQL artifacts, not runtime code.

## Suggested Work Order

1. Add the new session item type and pure constructors.
2. Port frontend scheduler to weighted bucket selection and active
   `SessionStudyItem` materialization.
3. Change backend session payload generation to emit synthetic action-backed
   review items and word buckets for learning/unstudied.
4. Change review attempt commits to validate and project from events without
   reading or updating `review_items`.
5. Port inspection/status reads.
6. Remove shadow/backfill scaffolding.
7. Remove table creation and update import/seed paths.
8. Run full tests and `npm run build`.

This order keeps the hardest dependency visible early: the frontend session
runtime. Once live session state no longer needs persisted review-item identity,
the database removal becomes mostly mechanical.

## Non-Goals For This Milestone

- moving learning and unstudied completions onto durable attempt-event
  projection
- adding contextual-selection scheduling
- changing recognition/production interval policy
- redesigning learning or unstudied covering criteria
- adding a durable action table

## Open Decisions

1. Should Home overview count due review skills or due review words admitted by
   the recency guard? This is not important for the first implementation pass.
2. For existing study databases, should milestone 6 include an automatic
   one-way table-drop migration, or should table removal wait until a manual DB
   migration/checkpoint is run? Defer this until runtime dependencies are closer
   to removed.
